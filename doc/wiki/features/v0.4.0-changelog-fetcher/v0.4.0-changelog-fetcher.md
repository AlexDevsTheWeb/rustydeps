# v0.4.0 — real registry changelog fetcher

## Motivation

Milestone 0.3.x briefings relied entirely on the model's internal knowledge, so
an unknown package or a recent release could produce confident but invented
changes. Milestone 0.4.0 grounds each request in the package's official release
notes first. The brief is
`doc/raw/2026-11-27/2026-11-27-v0.4.0-and-fixes.md` (Worktree 3).

## Lookup pipeline

For every dependency that misses the summary cache, `ChangelogFetcher`
(`src/registry/changelog.rs`) runs one bounded lookup before the chat request:

1. Resolve the repository URL from the registry metadata for the package's
   ecosystem (table below).
2. Extract `{owner, repo}` from a GitHub URL. GitLab, Bitbucket, `notgithub.com`,
   and `github.com.evil.example` resolve to `None`.
3. Ask `GET https://api.github.com/repos/{owner}/{repo}/releases/tags/{tag}`,
   trying the target version as published and with the `v` prefix toggled. When
   both miss, list up to 100 releases and match workspace tags such as
   `tokio-1.40.0`, `serde-v1.0.200`, or `crates/tokio/1.40.0`.
4. Sanitize the release body (normalize newlines, drop control characters,
   collapse blank runs), prepend the release name when it differs from the tag,
   and truncate to `MAX_CHANGELOG_CHARS` (1,500 characters).
5. Inject the excerpt into the user prompt as the primary source. Without notes,
   the previous knowledge-based prompt is used unchanged.

| Ecosystem | Metadata request | Repository field |
|-----------|------------------|------------------|
| Cargo | `crates.io/api/v1/crates/{name}` | `crate.repository` |
| npm | `registry.npmjs.org/{name}/latest` | `repository` (string or `{ url }`) |
| PyPI | `pypi.org/pypi/{name}/json` | `info.project_urls`, `home_page`, `project_url` |
| Composer | `repo.packagist.org/p2/{name}.json` | `source.url` of the matching (or first) version |
| Go | no request | `github.com/{owner}/{repo}` module paths |

## Budgets, privacy, and failure handling

- One lookup per package is capped at 8 seconds (`FETCH_TIMEOUT`); each HTTP
  request is capped at 5 seconds.
- The lookup runs only on a cache miss and only after the AI client exists, so a
  disabled summarizer, a cache hit, `--offline`, or a fatal provider error costs
  no registry or GitHub traffic.
- `GITHUB_TOKEN` or `GH_TOKEN` is optional. Authenticated requests raise the
  GitHub API limit from 60 to 5,000 per hour; the token never leaves the process.
- Missing repositories, non-GitHub hosts, 404 tags, rate limits, timeouts, and
  empty bodies all degrade to `None`; the scan and the ungrounded prompt continue.
- `--offline` disables the fetcher as well as registry version lookups.

## Cache compatibility

`CachedSummary::prompt_version` is now `2` (`CACHE_FORMAT_VERSION`). Entries from
v0.3.x deserialize with the default `0` and are treated as misses, so each
package is regenerated once with release-note grounding instead of serving a
lower-quality summary indefinitely. `cache clear` still removes every file.

## Tests

- `src/registry/changelog.rs` — GitHub URL parsing (HTTPS, `git+`, SSH, `.git`,
  trailing paths, lookalike hosts), tag candidates, workspace-tag matching and
  the release-list fallback, character-safe truncation, control-character
  cleanup, release composition, per-ecosystem resolution (Cargo, npm scoped,
  PyPI, Composer, Go), missing notes, and a disabled fetcher.
- `src/ai/prompt.rs` — excerpt injection, 1,500-character bound, and the
  knowledge-based fallback.
- `src/ai/cache.rs` — stale prompt versions and legacy entries are misses.
- `tests/ai_integration_tests.rs` — summarizer tests disable the fetcher so they
  never touch the network.
